Dependencias instaladas: `express`, `knex`, `pg` (driver de PostgreSQL), `dotenv`, `bcryptjs` (hash de contraseñas) y `nodemon` (desarrollo).

**¿Por qué `migration-helpers.js` no está dentro de `migrations/`?** Knex ejecuta como migración *cualquier* `.js` de esa carpeta.

## Paso 2 — Configuración

- `src/config/env.js` valida al arrancar que existan las variables obligatorias. Si falta `DB_PASSWORD`, la app falla de inmediato con un mensaje claro en lugar de un error raro de conexión más adelante.
- `src/config/database.js` crea **una sola** instancia de Knex para toda la app y ajusta dos conversiones del driver:
  - `NUMERIC → Number` (por defecto `pg` devuelve el dinero como texto).
  - `DATE → 'YYYY-MM-DD'` (evita que una fecha se corra un día por zona horaria).

## Paso 5 — Verificación

Se probó todo contra un PostgreSQL 18 temporal (no se tocó la BD local):

- ✅ `migrate:latest` crea las 13 migraciones.
- ✅ `migrate:rollback --all` las deshace todas y se pueden volver a crear.
- ✅ Seeds ejecutados dos veces seguidas sin duplicar datos.
- ✅ La BD **rechaza**: cédula duplicada, indicativo sin `+`, 4.ª foto, codeudor = deudor, crédito mensual sin tasa, crédito quincenal cuyas cuotas no cubren el capital, cuota ≠ capital + interés, pago ≠ capital + interés, borrar un crédito con pagos.
- ✅ La BD **acepta**: la misma cédula después de borrar lógicamente al cliente anterior, créditos válidos de ambas frecuencias.
- ✅ El trigger actualiza `updated_at`.

🐞 **Bug encontrado y corregido en la prueba:** la validación del indicativo usaba `'^\+...'` dentro de un string de JavaScript. En JS `"\+"` es solo `"+"`, así que el patrón llegaba roto a Postgres. Se cambió por `'^[+][0-9]{1,4}$'`, que no necesita escape.

## Paso 6 — Convención de nombres (acordada)

| Dónde | Estilo | Ejemplo |
|---|---|---|
| Tablas y columnas de PostgreSQL | snake_case | `principal_amount`, `loan_installments` |
| Variables, funciones y propiedades en JS | camelCase | `principalAmount`, `findById()` |
| Clases | PascalCase | `ClientService`, `ClientRepository` |
| Archivos | minúsculas con punto por capa | `client.repository.js`, `client.service.js` |
| Migraciones y seeds | snake_case (usan los nombres reales de las columnas) | `table.string('full_name')` |

**Cómo funciona la traducción automática** (`src/config/database.js` + `src/utils/case-converter.js`):

- `wrapIdentifier`: cuando el código escribe `where({ nationalId: '123' })`, Knex genera `WHERE "national_id" = '123'`.
- `postProcessResponse`: cuando Postgres devuelve `{ full_name: 'Ana' }`, el código recibe `{ fullName: 'Ana' }`.

La conversión es superficial: solo cambia nombres de columnas, nunca el contenido de un valor (por ejemplo, el interior de una columna JSON).

Solo se aplica a la conexión de la app. El CLI de Knex (migraciones y seeds) usa `knexfile.js` sin conversión, por eso ahí se escriben los nombres reales en snake_case.

✅ Verificado contra una base temporal: SQL generado, `insert ... returning`, `.first()`, `update` (devuelve un número sin tocar), `knex.raw` y lectura de los datos sembrados.

## Paso 7 — Esqueleto de Express (tarjeta Trello "[Backend] Esqueleto de Express")

Nuevas dependencias: `helmet` (cabeceras de seguridad), `cors` (qué frontends pueden llamar la API), `morgan` (log de peticiones), `zod` (validación de datos de entrada).

### Archivos nuevos

```
src/
├── server.js                  ← ARRANCA: crea el contenedor, la app y escucha el puerto
├── app.js                     ← CONSTRUYE la app Express (middlewares + rutas), sin arrancarla
├── container.js               ← ARMA las piezas: crea repositorios → servicios → controladores
├── config/validation.js       ← mensajes de Zod en español
├── errors/
│   ├── app-error.js           ← errores esperados: ValidationError(400), Unauthorized(401),
│   │                            Forbidden(403), NotFound(404), Conflict(409)
│   └── database-error-mapper.js ← traduce errores de Postgres (duplicado, FK, check) a esos errores
├── middlewares/
│   ├── validate-request.js    ← valida params/query/body con un esquema Zod
│   ├── not-found-handler.js   ← 404 para rutas que no existen
│   └── error-handler.js       ← ÚLTIMA parada de todo error → respuesta JSON uniforme
├── routes/index.js            ← monta todas las rutas bajo /api
└── (health) repository → service → controller → routes  ← primer módulo de ejemplo
```

Se agregaron dos carpetas además de las 5 acordadas: `middlewares/` y `errors/`. No son capas de negocio, son piezas compartidas por todos los módulos.

### Recorrido de una petición

```
GET /api/health
  │
  ├─ morgan        → escribe la línea en el log
  ├─ helmet        → agrega cabeceras de seguridad
  ├─ cors          → ¿el origen está permitido?
  ├─ express.json  → convierte el body a objeto (si es JSON inválido → 400)
  │
  ├─ routes/index.js → health.routes.js
  │     └─ (en otros módulos aquí va validateRequest y, luego, la autenticación)
  ├─ HealthController.getStatus   → solo HTTP: lee la petición, responde
  ├─ HealthService.getStatus      → la regla: "ok" si la BD responde, si no "degraded"
  └─ HealthRepository.ping        → solo datos: SELECT 1
  
Si algo lanza un error en cualquier punto → error-handler.js → JSON de error
```

### Formato de respuestas (contrato para el frontend)

```jsonc
// Éxito
{ "data": { ... } }

// Error (siempre igual)
{ "error": { "code": "VALIDATION_ERROR", "message": "Texto para el usuario", "details": [ ... ] } }
```

En producción, un error inesperado (bug) nunca muestra detalles técnicos al usuario: solo "Ocurrió un error inesperado." y el detalle va al log del servidor.

### SOLID en el esqueleto

| Principio | Dónde se ve |
|---|---|
| **S** – Responsabilidad única | Controller = HTTP, Service = reglas, Repository = datos. `app.js` construye, `server.js` arranca |
| **O** – Abierto/cerrado | Un módulo nuevo se agrega en `container.js` y `routes/index.js` sin modificar los existentes |
| **L** – Sustitución de Liskov | Todas las subclases de `AppError` sirven donde se espera un `AppError`; el error-handler no distingue cuál es |
| **I** – Segregación de interfaces | Cada servicio recibe solo lo que usa (`{ healthRepository }`), no "toda la app" |
| **D** – Inversión de dependencias | Nadie hace `new` de sus dependencias ni `require` de la BD: las recibe por constructor desde `container.js`. En pruebas se le pasa un repositorio falso |

### Decisiones

- **Express 5**: los errores de funciones `async` llegan solos al error-handler (no hace falta envolver cada ruta en try/catch).
- **`req.validated`**: en Express 5 `req.query` es de solo lectura, así que los datos ya validados y limpios (números convertidos, textos recortados, valores por defecto) quedan en `req.validated.{params,query,body}`. Los controladores leen de ahí, nunca de `req.body` directo.
- **Mensajes al usuario en español, código en inglés**: los textos de error son lo que verá Wilson en pantalla.
- **Cierre ordenado** (`SIGINT`/`SIGTERM`): deja terminar las peticiones en curso (ej. un pago guardándose) antes de cerrar la conexión a la BD.

### Verificación

- ✅ `GET /api/health` → 200 con `database: "up"` y cabeceras de helmet; sin `X-Powered-By`.
- ✅ Con la BD apagada → 503 `status: "degraded"` (el servidor no se cae).
- ✅ Ruta inexistente → 404; JSON mal formado → 400 `INVALID_JSON`.
- ✅ CORS: responde al origen permitido, ignora otros.
- ✅ Validación: convierte `"7"` → `7`, aplica valores por defecto, recorta espacios; agrupa todos los errores de params/query/body en una sola respuesta.
- ✅ Error de Postgres por duplicado → 409 `CONFLICT`.
- ✅ Bug → 500 con detalle en desarrollo, sin detalle en producción.
- 🔧 Ajuste tras probar: `morgan` se movió al inicio para que también registre las peticiones rechazadas por JSON inválido.

## Cómo correrlo en tu máquina

```bash
cd Backend
cp .env.example .env          # y pon tu usuario/contraseña de PostgreSQL
# crear la base de datos (una sola vez):
psql -U postgres -c "CREATE DATABASE loan_management;"
npm run db:migrate            # crea las tablas
npm run db:seed               # datos iniciales
npm run db:rollback:all       # (si quieres deshacer todo)
npm run dev                   # arranca la API con recarga automática
# probar: abrir http://localhost:3000/api/health en el navegador
```

### Preguntas de negocio abiertas (afectan la proyección de cuotas, no el esquema)

1. **Quincenal:** ¿las fechas son fijas (ej. 15 y 30 de cada mes) o cada 15 días contados desde el inicio? ¿Qué significa "día de pago" en este caso?
2. **Mensual:** ¿se cobra solo interés y el capital se abona cuando el cliente quiera, o hay un plazo fijo de meses? (El esquema soporta ambos: `number_of_installments` nulo = sin plazo.)
3. **Pagos parciales:** ¿se aplica primero al interés y luego al capital?
4. **Redondeo:** ¿las cuotas se redondean (a $100, a $1.000)?
5. **Mora:** ¿se cobra recargo por atraso? (No está en la cotización.)
