## La idea central: almacenamiento intercambiable

Todavía no hay cuenta de Cloudflare R2. En vez de bloquearnos, se construyeron **dos almacenamientos con la misma interfaz**:

| | `LocalFileStorage` | `R2FileStorage` |
|---|---|---|
| Para | Desarrollo | Producción |
| Dónde quedan los archivos | Carpeta `storage/` del servidor (ignorada por Git) | Bucket privado de Cloudflare R2 |
| Enlaces para ver la foto | `/api/files/...?expires=...&signature=...` (firmados con HMAC) | URL prefirmada de R2 |
| Métodos | `put`, `delete`, `getSignedUrl` | `put`, `delete`, `getSignedUrl` |

Se elige con `STORAGE_DRIVER=local` o `STORAGE_DRIVER=r2` en el `.env`. El servicio de fotos no sabe cuál está usando: **pasar a R2 es cambiar la configuración, no el código.**

En SOLID: es la **L** (cualquiera de los dos funciona donde se espera "un almacenamiento") y la **D** (el servicio depende de esa interfaz, no de Cloudflare ni del disco). El archivo `storage/create-file-storage.js` es el único que decide cuál crear.

## ¿Por qué enlaces firmados y no una ruta protegida con sesión?

Una etiqueta `<img src="...">` del navegador **no puede enviar** la cabecera `Authorization: Bearer`. Las opciones eran fotos públicas (inaceptable: incluyen cédulas) o enlaces que llevan su propia autorización. El enlace firmado dice "este archivo, hasta esta hora", con una firma que solo el servidor puede producir. Si alguien cambia una letra o se pasa la hora → 403.

El almacenamiento local imita exactamente ese comportamiento, así que en desarrollo se prueba lo mismo que pasará en producción.

## Endpoints

| Método | Ruta | Permiso |
|---|---|---|
| GET | `/api/clients/:clientId/photos` | `clients.read` |
| PUT | `/api/clients/:clientId/photos/:position` (1–3) | `clients.update` |
| DELETE | `/api/clients/:clientId/photos/:position` | `clients.update` |

`PUT` y no `POST`: significa "pon esta foto en el espacio 2". Si ya había una, la reemplaza. Así el máximo de 3 lo garantiza la propia ruta (y la BD con su CHECK), sin contar fotos.

## Qué le pasa a cada foto (`ImageProcessor`)

1. **Se verifica el contenido real**: un PDF renombrado a `.jpg` se rechaza (no se confía en el nombre ni en el tipo que dice el navegador).
2. **Se endereza** según la orientación EXIF del celular (si no, muchas fotos se verían de lado).
3. **Se reduce** a máximo 1600 px, JPEG calidad 80 (nunca se agranda una foto pequeña).
4. **Miniatura** 320×320 para listas.
5. **Se borran todos los metadatos**: ubicación GPS donde se tomó, modelo del teléfono, etc. Importante con datos personales.

## Consistencia entre archivos y base de datos (`ClientPhotoService`)

Archivos y filas viven en sistemas distintos y no hay una transacción que cubra ambos. Regla: **la BD manda**.

- **Subir**: primero se suben los archivos y luego se guarda la fila. Si guardar falla, se borran los archivos recién subidos (no quedan huérfanos).
- **Reemplazar/borrar**: primero cambia la fila y luego se borran los archivos viejos. Si ese borrado falla, se registra en el log pero el usuario no ve error (un archivo huérfano no daña nada; una fila apuntando a un archivo inexistente sí).
- **Dos subidas simultáneas al mismo espacio**: el repositorio bloquea la fila (`SELECT ... FOR UPDATE`) dentro de una transacción.
- Las llaves internas de almacenamiento nunca salen en la API: el frontend solo recibe enlaces temporales.

## Seguridad del almacenamiento local

- Las llaves solo admiten el patrón `clients/<id>/<uuid>.jpg`; cualquier `../` se rechaza antes de tocar el disco.
- La firma se compara en tiempo constante.
- El secreto de los enlaces se **deriva** de `JWT_SECRET` (HMAC con otro propósito): nunca es el mismo secreto que firma las sesiones.
- Helmet bloquea por defecto que otro origen use las imágenes (`Cross-Origin-Resource-Policy: same-origin`). Solo la ruta de archivos lo abre a `cross-origin`, porque el frontend corre en otro puerto/dominio. El resto de la API sigue en `same-origin`.
