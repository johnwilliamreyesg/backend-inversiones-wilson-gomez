## Paso 1 — Validación de entrada (`src/validators/`)

Carpeta nueva: aquí viven los esquemas Zod que definen **qué datos acepta la API**.

- `common.validators.js` — piezas reutilizables por todos los módulos:
  - `idParamSchema`: el `:id` de la URL debe ser un entero positivo (`"7"` → `7`).
  - `paginationSchema`: `page` y `pageSize` (20 por defecto, máximo 100).
  - `optionalText(max)`: recorta espacios y convierte `""` en `null`.
- `client.validators.js` — reglas del cliente (las mismas de los CHECK de la BD):
  - Nombre 3–150 caracteres, recortado.
  - Cédula 3–20 letras/números/guiones, **en mayúsculas** (así `ab-100` y `AB-100` son la misma).
  - Teléfono: acepta `300 123-4567` y guarda `3001234567`.
  - Indicativo `+57` por defecto.
  - Para editar (`PATCH`) todos los campos son opcionales, pero al menos uno es obligatorio.

**Idea clave:** el validador no solo rechaza, también **normaliza**. El servicio siempre recibe datos limpios.

## Paso 3 — Servicio (reglas de negocio)

`client.service.js`:

| Regla | Error |
|---|---|
| Cliente inexistente o eliminado | 404 `El cliente no existe.` |
| Cédula ya registrada en otro cliente activo (al crear o editar) | 409 `Ya existe un cliente con la cédula X: Nombre.` |
| Eliminar un cliente con créditos abiertos como deudor **o codeudor** | 409 `No se puede eliminar: el cliente tiene N crédito(s) abierto(s)…` |
| Al crear se registra quién lo creó (`createdBy`) | — (será el usuario logueado cuando exista autenticación) |

La BD también rechaza la cédula duplicada (índice único), pero el servicio revisa antes para dar un mensaje con el nombre del cliente existente.

### 🐞 Lo que encontraron las pruebas y se corrigió

1. **Cédulas cortas rechazadas.** El mínimo era 4 y rechazó la cédula `200`. En Colombia hay cédulas antiguas muy cortas, y rechazar a un cliente real es peor → mínimo bajado a 3.
2. **Búsqueda sensible a tildes.** Buscar `gomez` no encontraba `Gómez`: un cobrador escribiendo en el celular no encontraría al cliente. Solución:
   - Nueva migración `20261024000100_enable_unaccent_extension` (extensión `unaccent` de PostgreSQL).
   - El repositorio busca con `unaccent(full_name) ILIKE unaccent('%texto%')`.
   - Probado con un usuario **no superusuario** dueño de la BD (como en un hosting): funciona, porque `unaccent` es una extensión "confiable" desde PostgreSQL 13.

> Nota: al probar con `curl` desde la consola de Windows, las tildes se ven como `�`. Es la consola, no la API. Enviando los datos desde un archivo UTF-8 llegan exactos.

Y ahora **todas las rutas de clientes exigen sesión y permiso** (`clients.read`, `clients.create`, `clients.update`, `clients.delete`).

### Archivos nuevos

```
src/
├── security/                       ← carpeta nueva: adaptadores de librerías de seguridad
│   ├── password-hasher.js          ← envuelve bcrypt (hash / compare), costo 12
│   └── token-provider.js           ← envuelve jsonwebtoken (sign / verify), HS256 fijo
├── migrations/20261024000200_add_token_version_to_users.js
├── repositories/user.repository.js ← usuarios (perfil público vs. credenciales)
├── repositories/role.repository.js ← permisos de un rol
├── services/auth.service.js        ← login, resolver usuario del token, cambiar contraseña
├── validators/auth.validators.js
├── middlewares/authenticate.js     ← "¿quién eres?" → req.user (401 si no)
├── middlewares/authorize.js        ← "¿puedes hacer esto?" → 403 si no
├── middlewares/rate-limiters.js
├── controllers/auth.controller.js
└── routes/auth.routes.js
```

**¿Por qué `security/`?** `PasswordHasher` y `TokenProvider` no son reglas de negocio, son adaptadores de librerías. El servicio depende de "algo que compara contraseñas", no de bcrypt (inversión de dependencias). En las pruebas se reemplazan por versiones falsas instantáneas, y si algún día se cambia de librería solo se toca ese archivo.

### Cómo funciona una petición protegida

```
GET /api/clients   (Authorization: Bearer eyJ...)
  │
  ├─ authenticate
  │    ├─ TokenProvider.verify  → firma válida, no caducado, algoritmo HS256 → { userId, tokenVersion }
  │    ├─ UserRepository        → ¿existe?, ¿activo?, ¿tokenVersion coincide?
  │    └─ RoleRepository        → permisos del rol  →  req.user = { id, ..., permissions }
  ├─ authorize('clients.read')  → ¿req.user.permissions lo incluye?  (403 si no)
  ├─ validateRequest
  └─ ClientController ...
```

Se consulta la BD en cada petición (son 3 consultas pequeñas). A cambio, **desactivar un usuario, cambiar su contraseña o quitarle un permiso aplica de inmediato**, sin esperar a que caduque el token. Para el volumen de este negocio el costo es despreciable.

### Decisiones de seguridad

| Decisión | Por qué |
|---|---|
| Mismo mensaje para "correo no existe" y "contraseña errada" | El login no sirve para averiguar qué correos están registrados |
| Si el correo no existe, igual se compara contra un hash de relleno | Ambos fallos tardan lo mismo (~240 ms medidos): el tiempo de respuesta tampoco delata nada |
| `token_version` en `users` | Al cambiar la contraseña sube +1 y todos los tokens anteriores mueren (celular perdido = sesión cerrada). El dispositivo que la cambió recibe un token nuevo |
| El token solo lleva `sub` (id) y `tokenVersion` | Sin permisos ni datos personales dentro: se leen frescos de la BD |
| Algoritmo HS256 fijado al verificar | Bloquea tokens `alg: none` y ataques de confusión de algoritmo |
| `JWT_SECRET` de mínimo 32 caracteres | El servidor **no arranca** si falta o es corto. Se valida al arrancar el servidor (no en `env.js`) para que las migraciones sigan funcionando sin él |
| 10 logins fallidos / 15 min por IP | Frena adivinar contraseñas. Los exitosos no cuentan |
| Contraseña nueva: 8+ caracteres, letra y número, máx. 72 bytes | bcrypt ignora en silencio lo que pase de 72 bytes; mejor rechazarlo |
| Costo de bcrypt 12 (antes 10 en el seed) | Más lento de atacar; el seed ahora usa el mismo `PasswordHasher` |

```bash
# 1. Agregar a tu .env (sin esto el servidor no arranca):
#    JWT_SECRET=<generar con el comando de abajo>
#    JWT_EXPIRES_IN=12h
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

npm run db:migrate     # aplica las 2 migraciones nuevas (unaccent, token_version)
npm run db:seed        # crea el admin si aún no existe

# 2. Login → copiar el token → usarlo como "Bearer Token" en Thunder Client

#    { "email": "<ADMIN_EMAIL del .env>", "password": "<ADMIN_PASSWORD del .env>" }
```
